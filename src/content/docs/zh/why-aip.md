## 重复的工作 {#repeated-work}

一个典型的 Web 功能每次都要经历相同的步骤：

1. 前端定义所需的数据。
2. 后端实现提供这些数据的 API。
3. 双方维护请求与响应的契约。
4. 功能变化时，两侧一起修改。
5. 类似的功能又会新增一个 API 和实现。

每一步都会留下代码：route、controller、service、DTO、校验、授权检查、repository、错误处理和 API 文档。它们都会成为需要维护的部分。

## 为什么仅靠 AI 解决不了 {#ai-does-not-fix-it}

AI 编码智能体可以很快地写出这些代码，但需要这些代码的结构没有改变：每个新页面仍然意味着两侧的新契约，每次修改仍要做两遍。更快地生成同样的层，维护成本依旧。

现有框架是在"由人编写、阅读和维护代码"的前提下发展起来的。在 AI 承担大部分实现与修改的时代，AIP 重新审视这一前提。

> AIP 不止于让 AI 更好地编写现有结构的代码，而是从结构上减少那些本来就必须编写和维护的代码。

## AIP 的做法 {#what-aip-does}

- **前端表达所需。** 字段选择、关联数据、过滤、排序与分页、服务器允许的简单修改，以及对标准操作或扩展的调用，都由调用方表达，而不是再实现一个 endpoint。目标是 `Decided`，具体形式是 `Open`。
- **服务器按设计内置标准能力。** 像 Spring Boot 应用一样，AIP 服务器在安装和配置后于自己的端口启动。与空应用不同，它一开始就具备丰富的标准能力。`Decided`
- **由策略而不是调用方决定。** 能够表达一个请求并不等于获准执行。服务器会根据契约和策略检查每一个请求。`Decided`
- **其余部分由扩展负责。** 标准能力无法表达的逻辑，在同样的契约下以 JavaScript/TypeScript 或 Python 官方扩展编写。`Decided`

## 与熟悉方式的区别 {#comparison}

| 方式 | 每个功能的工作留在哪里 |
|---|---|
| REST | 每个需求都需要新的 endpoint 及其后端实现 |
| GraphQL | 调用方选择数据，但服务器仍要为 schema 实现 resolver 和授权 |
| AIP | 调用方表达数据和操作，共享运行时在声明的策略下执行，只有应用特有的逻辑以扩展编写 |

AIP 借鉴了 GraphQL 的数据选择与组合思想和 CQRS 的关注点分离，但不复制任何一方。AIP 一行描述的是设计目标。各部分实现到什么程度，记录在[项目状态](/zh/docs/status/)中。

## 不做的承诺 {#non-goals}

- 后端不会消失。职责依然存在，AIP 把反复实现这些职责的工作移到共享的基础设施中。
- 不声称任何生产力或性能数字。目前尚未测量。
