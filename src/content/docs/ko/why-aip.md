## 반복되는 작업 {#repeated-work}

일반적인 웹 기능은 매번 같은 단계를 거친다.

1. 프론트엔드가 필요한 데이터를 정의한다.
2. 백엔드가 그 데이터를 제공할 API를 구현한다.
3. 양쪽이 요청과 응답의 계약을 관리한다.
4. 기능이 바뀌면 양쪽이 함께 바뀐다.
5. 비슷한 기능에도 또 다른 API와 구현이 추가된다.

단계마다 코드가 남는다. route, controller, service, DTO, 검증, 권한 검사, repository, 오류 처리, API 문서. 그 모두가 유지보수 대상이 된다.

## AI만으로는 해결되지 않는 이유 {#ai-does-not-fix-it}

AI 코딩 에이전트는 이 코드를 빠르게 만들 수 있다. 하지만 그 코드를 요구하는 구조는 그대로다. 새 화면마다 양쪽에 새 계약이 생기고, 모든 변경을 두 번 해야 한다. 같은 계층을 더 빨리 생성해도 유지보수 비용은 같다.

기존 프레임워크는 사람이 코드를 쓰고 읽고 유지보수한다는 전제 위에서 발전했다. AIP는 AI가 구현과 수정의 상당 부분을 맡는 시대에 그 전제를 다시 검토한다.

> AIP는 AI가 기존 구조의 코드를 더 잘 작성하게 만드는 데 그치지 않는다. 애초에 작성하고 유지보수해야 하는 코드 자체를 구조적으로 줄인다.

## 대신 AIP가 하는 일 {#what-aip-does}

- **프론트엔드가 필요한 것을 표현한다.** 필드 선택, 관계 데이터, 필터, 정렬과 페이지네이션, 서버가 허용한 단순 변경, 표준 동작이나 확장 호출을 endpoint를 하나 더 구현하는 대신 호출자가 표현한다. 목표는 `Decided`, 구체 형태는 `Open`.
- **서버는 표준 기능을 내장하도록 설계한다.** Spring Boot 애플리케이션처럼 AIP 서버도 설치하고 설정하면 자체 포트에서 시작한다. 빈 애플리케이션과 달리 처음부터 풍부한 표준 기능을 갖춘다. `Decided`
- **판단은 호출자가 아니라 정책이 한다.** 요청을 표현할 수 있다는 것이 실행 권한은 아니다. 서버는 모든 요청을 계약과 정책에 비춰 확인한다. `Decided`
- **나머지는 확장이 맡는다.** 표준 기능으로 표현할 수 없는 로직은 같은 계약 아래에서 JavaScript/TypeScript나 Python 공식 확장으로 쓴다. `Decided`

## 익숙한 방식과의 차이 {#comparison}

| 방식 | 기능별 작업이 남는 곳 |
|---|---|
| REST | 필요마다 새 endpoint와 그 백엔드 구현 |
| GraphQL | 호출자가 데이터를 고르지만 서버는 schema의 resolver와 권한을 여전히 구현한다 |
| AIP | 호출자가 데이터와 동작을 표현하고, 공통 런타임이 선언된 정책 아래에서 실행한다. 애플리케이션 고유 로직만 확장으로 쓴다 |

AIP는 GraphQL의 데이터 선택·조합 개념과 CQRS의 관심사 분리에서 영감을 받았지만 어느 쪽도 복제하지 않는다. AIP 행은 설계의 목표다. 각 부분이 어디까지 실현됐는지는 [현재 상태](/ko/docs/status/)에서 추적한다.

## 약속하지 않는 것 {#non-goals}

- 백엔드는 사라지지 않는다. 책임은 그대로 남고, 그 책임을 매번 다시 구현하는 일을 AIP가 공통 기반으로 옮긴다.
- 생산성이나 성능 수치를 주장하지 않는다. 아직 측정한 적이 없다.
