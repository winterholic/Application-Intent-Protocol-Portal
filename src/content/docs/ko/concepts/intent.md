## endpoint에서 intent로 {#endpoints-to-intent}

REST API에서 호출자의 필요는 백엔드 개발자가 그 목적으로 구현한 URL과 HTTP method로 표현된다. AIP에서 중요한 것은 그 목적으로 만들어진 전송 경로가 아니라 애플리케이션이 하려는 일이다.

아래 두 줄은 사고방식의 전환을 보여 줄 뿐이다. 두 번째 줄은 **AIP 문법이 아니다**. AIP 문법은 `Open`이다.

```text
POST /api/orders/:id/approve      # a route someone had to implement
approve(order)                    # the intent the application actually has
```

## 호출자가 표현할 수 있는 것 {#what-callers-express}

창시자는 프론트엔드의 표현이 지금 백엔드에서 반복 작성하는 상당 부분을 대체하기를 원했다. 검토 범위는 다음과 같다.

| 표현 | 상태 |
|---|---|
| 특정 필드 선택 | 목표로 `Decided` |
| 관계 데이터 조회 | 목표로 `Decided` |
| 조건부 필터링 | 목표로 `Decided` |
| 정렬과 페이지네이션 | 목표로 `Decided` |
| 서버가 허용한 단순 데이터 변경 | 목표로 `Decided` |
| 표준 동작의 호출과 조합 | 목표로 `Decided`. 원자적 조합 범위는 `Open` |
| 복잡한 업무 로직을 위한 확장 호출 | `Decided` |

읽기는 호출자 중심이다. 새 화면은 필요한 데이터를 조합해 요청하고, 서버는 정책에 따라 실행한다. 새 화면마다 서버 API를 추가해야 한다면 AIP는 목적을 놓친다. `Decided`

## 서버에 남는 것 {#what-the-server-decides}

요청을 표현한다고 실행 권한이 생기지 않는다. 서버는 모든 요청을 계약과 정책에 비춰 확인하고, 다음 책임을 계속 진다.

- 인증과 인가
- 데이터 접근 통제
- 업무 불변조건과 데이터 무결성
- 트랜잭션
- 실행 비용과 자원 제한
- 외부 연동에 대한 통제
- 실행과 운영의 안정성

정책 밖의 임의 쿼리를 금지하는 것과 정책 안의 안전한 조합까지 금지하는 것은 다르다. AIP는 후자를 허용하고 전자를 거부한다.

## 열린 질문 {#open}

- 새 필드를 명시적으로 열기 전까지 호출자에게 숨길지. `Direction`: 안전한 기본값으로 제안됨.
- 운영 환경에서 미리 등록하지 않은 읽기 형태를 받을지. `Direction`: 보안·성능·비용 검증을 전제로 정책 안에서 허용.
- 첫 출시에서 누가 요청을 직접 작성할 수 있는지: 자사 프론트엔드, AI 에이전트, 파트너, 불특정 서드파티. `Open`
- 호출자가 쓰기를 조합할 자유의 범위와 트랜잭션 경계. `Open`
