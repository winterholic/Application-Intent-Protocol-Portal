## endpoint から intent へ {#endpoints-to-intent}

REST API では、呼び出し側の必要は、バックエンド開発者がその目的のために実装した URL と HTTP メソッドとして表されます。AIP で重要なのは、そのために作られた転送経路ではなく、アプリケーションが何をしようとしているかです。

次の二行は考え方の転換を示すだけです。二行目は **AIP の構文ではありません**。AIP の構文は `Open` です。

```text
POST /api/orders/:id/approve      # a route someone had to implement
approve(order)                    # the intent the application actually has
```

## 呼び出し側が表現できるもの {#what-callers-express}

創設者は、フロントエンドの表現が今バックエンドで繰り返し書かれている部分の多くを置き換えることを求めました。検討範囲は次のとおりです。

| 表現 | ステータス |
|---|---|
| 特定フィールドの選択 | 目標として `Decided` |
| 関連データの取得 | 目標として `Decided` |
| 条件付きフィルタリング | 目標として `Decided` |
| ソートとページネーション | 目標として `Decided` |
| サーバーが許可した単純なデータ変更 | 目標として `Decided` |
| 標準操作の呼び出しと組み合わせ | 目標として `Decided`。アトミックな組み合わせの範囲は `Open` |
| 複雑な業務ロジックのための拡張呼び出し | `Decided` |

読み取りは呼び出し側中心です。新しい画面は必要なデータを組み合わせて要求し、サーバーがポリシーに従って実行します。新しい画面のたびにサーバー API を追加する必要があるなら、AIP は目的を果たせません。`Decided`

## サーバーに残るもの {#what-the-server-decides}

リクエストを表現しても実行の権限は生まれません。サーバーはすべてのリクエストを契約とポリシーに照らして確認し、次の責任を持ち続けます。

- 認証と認可
- データアクセス制御
- 業務上の不変条件とデータ整合性
- トランザクション
- 実行コストとリソース制限
- 外部連携の統制
- 実行と運用の安定性

ポリシー外の任意のクエリを禁止することと、ポリシー内の安全な組み合わせまで禁止することは別です。AIP は後者を許可し、前者を拒否します。

## 未解決の問い {#open}

- 新しいフィールドを明示的に公開するまで呼び出し側から隠すか。`Direction`: 安全な既定値として提案されている。
- 本番環境で事前登録されていない読み取りの形を受け付けるか。`Direction`: セキュリティ・性能・コストの検証を前提に、ポリシーの範囲で許可。
- 最初のリリースで誰がリクエストを直接書けるか: 自社フロントエンド、AI エージェント、パートナー、不特定のサードパーティ。`Open`
- 呼び出し側が書き込みを組み合わせる自由の範囲とトランザクション境界。`Open`
