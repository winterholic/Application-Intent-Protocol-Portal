## 繰り返される作業 {#repeated-work}

一般的な Web 機能は毎回同じ手順をたどります。

1. フロントエンドが必要なデータを定義する。
2. バックエンドがそれを提供する API を実装する。
3. 両側がリクエストとレスポンスの契約を管理する。
4. 機能が変わると両側が一緒に変わる。
5. 似た機能にも、また別の API と実装が追加される。

手順ごとにコードが残ります。route、controller、service、DTO、検証、認可チェック、repository、エラー処理、API ドキュメント。そのすべてが保守の対象になります。

## AI だけでは解決しない理由 {#ai-does-not-fix-it}

AI コーディングエージェントはこのコードを素早く作れます。しかし、そのコードを必要とする構造は変わりません。新しい画面のたびに両側に新しい契約が生まれ、すべての変更を二度行う必要があります。同じ層を速く生成しても、保守のコストは同じです。

既存のフレームワークは、人がコードを書き、読み、保守するという前提で発展してきました。AIP は、AI が実装と修正の大部分を担う時代に、その前提を見直します。

> AIP は、AI が既存の構造のコードをうまく書けるようにすることにとどまりません。そもそも書いて保守しなければならないコードそのものを構造的に減らします。

## 代わりに AIP がすること {#what-aip-does}

- **フロントエンドが必要なものを表現する。** フィールドの選択、関連データ、フィルター、ソートとページネーション、サーバーが許可した単純な変更、標準操作や拡張の呼び出しを、endpoint をもう一つ実装する代わりに呼び出し側が表現します。目標は `Decided`、具体的な形は `Open`。
- **サーバーは標準機能を内蔵するよう設計する。** Spring Boot アプリケーションのように、AIP サーバーもインストールと設定の後に自前のポートで起動します。空のアプリケーションとは違い、最初から豊富な標準機能を備えます。`Decided`
- **判断するのは呼び出し側ではなくポリシー。** リクエストを表現できることは実行の許可ではありません。サーバーはすべてのリクエストを契約とポリシーに照らして確認します。`Decided`
- **残りは拡張が担う。** 標準機能で表現できないロジックは、同じ契約のもとで JavaScript/TypeScript または Python の公式拡張として書きます。`Decided`

## 見慣れた方式との違い {#comparison}

| 方式 | 機能ごとの作業が残る場所 |
|---|---|
| REST | 必要ごとに新しい endpoint とそのバックエンド実装 |
| GraphQL | 呼び出し側がデータを選ぶが、サーバーは schema の resolver と認可を引き続き実装する |
| AIP | 呼び出し側がデータと操作を表現し、共通ランタイムが宣言されたポリシーのもとで実行する。アプリ固有のロジックだけを拡張として書く |

AIP は GraphQL のデータ選択・組み合わせの考え方と CQRS の関心の分離から着想を得ていますが、どちらも複製しません。AIP の行は設計の目標です。各部分がどこまで実現したかは[現状](/ja/docs/status/)で追跡します。

## 約束しないこと {#non-goals}

- バックエンドは消えません。責任はそのまま残り、それを毎回実装し直す作業を AIP が共通基盤に移します。
- 生産性や性能の数値は主張しません。まだ測定していません。
